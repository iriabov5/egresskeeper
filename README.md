# EgressKeeper

Локальный контроль исходящих соединений для AI-агентов, MCP-серверов и
dev-инструментов: egress proxy, политики по host и port, живой поток решений — в
одном desktop-приложении на Tauri и Rust.

> **Статус: рабочий MVP.** Прокси применяет политики к реальному трафику,
> профили и правила редактируются в UI, решения видны в живом потоке.
> Сохранение решений, подпись сборок и автообновление — в roadmap.

## Проблема

AI-агенты, MCP-серверы и CLI-инструменты ходят в сеть от имени разработчика.
Периметральные средства (SWG, корпоративный firewall) не видят локальный процесс,
не знают, какому инструменту что разрешено, и не дают ответа на вопрос «куда
именно сейчас ходил этот агент».

## Решение

EgressKeeper запускает локальный egress proxy. Инструмент направляется на него
через `HTTP_PROXY` / `HTTPS_PROXY`. Для каждого соединения приложение:

1. определяет профиль, привязанный к listener'у;
2. применяет политику: правила по host и port и default action профиля;
3. разрешает соединение или отклоняет его **не обращаясь к цели**;
4. показывает решение в живом потоке с причиной — сработавшим правилом или
   default action.

```text
  AI agent / MCP server / dev tool
                 │  HTTP_PROXY=http://127.0.0.1:8787
                 ▼
        ┌──────────────────────────┐
        │  EgressKeeper (desktop)  │
        │  ┌────────────────────┐  │
        │  │ proxy runtime      │  │  Tokio + hyper: CONNECT и HTTP
        │  └─────────┬──────────┘  │
        │            ▼             │
        │  ┌────────────────────┐  │
        │  │ policy engine      │  │  профили, правила, default action
        │  └─────────┬──────────┘  │
        │            ▼             │
        │   решение ──▶ событие ──▶ │  живой поток решений
        │  ┌────────────────────┐  │
        │  │ UI (React + Vite)  │  │  только представление
        │  └────────────────────┘  │
        └─────────────┬────────────┘
                      ▼
                target server
```

## Быстрый старт

Требования: Rust stable (`rust-toolchain.toml`), Node.js 22+ и pnpm, на Linux —
`libwebkit2gtk-4.1-dev`, `libsoup-3.0-dev` и `libgtk-3-dev`.

```bash
pnpm install      # frontend-зависимости
pnpm tauri dev    # запуск desktop-приложения в dev-режиме
```

Три шага, чтобы увидеть продукт в работе:

1. На экране **«Политики»** добавьте правила: например, разрешите
   `127.0.0.1:8899` или `api.example.com`.
2. На экране **«Прокси»** добавьте listener (порт и профиль) и включите его.
3. Направьте инструмент на proxy и перезапустите его:

```bash
export HTTPS_PROXY=http://127.0.0.1:8787
export HTTP_PROXY=http://127.0.0.1:8787
export NO_PROXY=localhost,127.0.0.1
```

Проверка на `curl`:

```bash
curl -x http://127.0.0.1:8787 http://api.example.com/   # 403, если правила нет
curl -x http://127.0.0.1:8787 http://127.0.0.1:8787/   # 403: петля на сам proxy
```

## Трей и закрытие окна

Приложение не обязано жить в окне: proxy — это фоновый процесс, который
продолжает фильтровать трафик, пока инструмент работает.

- Закрытие окна по умолчанию **скрывает** его в трей; listeners продолжают
  работать. Пункт «Выход» в меню трея завершает приложение и останавливает
  listeners. Это поведение настраивается на экране «Настройки».
- Меню трея показывает состояние («proxy выключен», «работает listeners: 1»)
  и позволяет запустить или остановить все listeners, не открывая окно.
- Если трей недоступен на платформе, приложение работает как обычно, но
  закрытие окна завершает процесс — вместо тихого «закрыл, а оно живо» UI
  сообщает об этом явно.
- Автозапуск регистрируется средствами операционной системы. Frontend не
  получает API автозапуска: состояние читает и меняет только Rust через
  типизированную команду. Переключатель показывается только там, где система
  поддерживает автозапуск; в dev-режиме он зарегистрирует debug-сборку, поэтому
  проверять автозапуск нужно на установленном приложении.
- Автозапуск поднимает приложение, а приложение — listeners, включённые в
  конфигурации: отдельной настройки «запускать listeners при старте» нет.

## Политики

Политика — это профиль с default action и упорядоченным списком правил. Решение
принимает **первое совпавшее** правило; если ни одно правило не подошло,
применяется default action профиля. Новый профиль создаётся с запрещающим default
action: «забыл настроить» означает «ничего не разрешено».

| Сопоставление | `example.com` | `api.example.com` | `a.b.example.com` | `evil-example.com` |
| --- | --- | --- | --- | --- |
| Точный host `example.com` | ✅ | ❌ | ❌ | ❌ |
| Поддомены `*.example.com` | ❌ | ✅ | ✅ | ❌ |

Совпадение проверяется по границе метки, поэтому `evil-example.com` и
`example.com.evil.test` не совпадут ни с одним из вариантов. `*.example.com`
намеренно **не** покрывает сам домен: чтобы разрешить и его, нужно отдельное
правило.

## Архитектура

| Слой | Расположение | Ответственность |
| --- | --- | --- |
| UI | `src/` | Представление, ввод пользователя. Не содержит бизнес-логики |
| Application / domain | `crates/egresskeeper-core/src/{domain,application}` | Правила предметной области и сценарии использования |
| Infrastructure | `crates/egresskeeper-core/src/infrastructure` | Сеть, файловая система, SQLite |
| Tauri wiring | `src-tauri/` | Managed state, узкие команды, события, capabilities |

Ядро не зависит от Tauri и тестируется без GUI; frontend общается с backend
только через узкий типизированный IPC; один async-рантайм на процесс.

## Явные ограничения

EgressKeeper **не** делает следующего — это осознанная граница области
применимости:

- не перехватывает TLS, не расшифровывает трафик и не устанавливает собственный
  корневой сертификат;
- не выполняет packet capture и kernel-level filtering;
- не определяет, какой процесс установил соединение: принадлежность моделируется
  отдельным listener'ом на профиль;
- не является sandbox: инструмент, игнорирующий настройки proxy, не
  контролируется; защита от администратора машины не предоставляется;
- не поддерживает IDN: hostname с не-ASCII символами отклоняется с ошибкой
  валидации;
- не поддерживает wildcard в середине имени, правила по IP-диапазонам (CIDR) и
  фильтрацию по методу или пути HTTP;
- не сохраняет решения: живой поток решений живёт в памяти UI и очищается при
  перезапуске (сохранение — изменение `add-audit-store`);
- не запускается скрытым: автозапуск поднимает приложение вместе с включёнными
  listeners, но окно при этом открывается — старт сразу в трей требует
  отдельного изменения.
